1. Introduction to Multi-Agent Systems

In this hands-on lab, you will build a sophisticated multi-agent system where an LLM acts as a supervisor, coordinating multiple specialized worker agents. This pattern is powerful for complex tasks that require different capabilities or domain expertise.

Key Concepts:

  • Supervisor Pattern: A central agent (supervisor) decides which worker agent should handle each step of a task.
  • Specialized Agents: Each worker agent has specific tools and knowledge for a particular domain (inventory, orders, analytics).
  • State Management: LangGraph maintains state across agent interactions, allowing agents to build on each other's work.
  • Conditional Routing: The supervisor uses LLM reasoning to determine the next agent to invoke based on the current state.

In this example, we'll build a warehouse management system with three worker agents: InventoryManager, OrderProcessor, and AnalyticsManager, all orchestrated by an LLM supervisor.

2. Setting Up the Database

Before we can build our multi-agent system, we need a data source for our agents to work with. We'll create a SQLite database representing a warehouse with inventory, orders, and order items. This simulates a real-world scenario where agents need to query and update data.

Why SQLite? SQLite is a lightweight, file-based database perfect for prototyping and learning. Our agents will use SQL tools to interact with this database, demonstrating how agents can work with structured data.

import sqlite3
from typing import Annotated
from langchain_core.tools import tool
from langchain_experimental.tools import PythonREPLTool
import pandas as pd
from datetime import datetime, timedelta

# Initialize SQLite database with some tables
def init_database():
    conn = sqlite3.connect('warehouse2.db')
    c = conn.cursor()

    # Create tables
    c.execute('''CREATE TABLE IF NOT EXISTS inventory
                 (product_id TEXT PRIMARY KEY,
                  name TEXT,
                  quantity INTEGER,
                  reorder_point INTEGER,
                  unit_price REAL)''')

    c.execute('''CREATE TABLE IF NOT EXISTS orders
                 (order_id TEXT PRIMARY KEY,
                  order_date TIMESTAMP,
                  status TEXT,
                  total_amount REAL)''')

    c.execute('''CREATE TABLE IF NOT EXISTS order_items
                 (order_id TEXT,
                  product_id TEXT,
                  quantity INTEGER,
                  FOREIGN KEY(order_id) REFERENCES orders(order_id),
                  FOREIGN KEY(product_id) REFERENCES inventory(product_id))''')

    # Insert sample data
    c.execute('DELETE FROM inventory')
    c.execute('DELETE FROM orders')
    c.execute('DELETE FROM order_items')

    # Sample inventory
    inventory_data = [
        ('SKU001', 'Gaming Laptop', 45, 20, 999.99),
        ('SKU002', 'Wireless Mouse', 150, 50, 29.99),
        ('SKU003', 'Mechanical Keyboard', 5, 30, 89.99),
        ('SKU004', 'Monitor 27"', 30, 15, 299.99),
        ('SKU005', 'USB-C Hub', 10, 40, 49.99)
    ]
    c.executemany('INSERT INTO inventory VALUES (?,?,?,?,?)', inventory_data)

    # Sample orders
    for i in range(1, 21):  # Create 20 sample orders
        order_id = f'ORD{i:03d}'
        order_date = datetime.now() - timedelta(days=i)
        status = ['Pending', 'Processing', 'Shipped', 'Delivered'][i % 4]
        c.execute('INSERT INTO orders VALUES (?,?,?,?)',
                 (order_id, order_date, status, 0))  # Total will be updated

        # Add 1-3 items to each order
        for j in range(1, (i % 3) + 2):
            product_id = f'SKU{(i + j) % 5 + 1:03d}'
            quantity = (i + j) % 5 + 1
            c.execute('INSERT INTO order_items VALUES (?,?,?)',
                     (order_id, product_id, quantity))

    conn.commit()
    conn.close()

# Initialize the database
init_database()

What this does: This function creates three tables (inventory, orders, order_items) and populates them with sample data. The inventory table tracks products with their quantities and reorder points. The orders table stores order information, and order_items links orders to products. This gives us realistic data for our agents to work with.

4. Creating Specialized Worker Agents

Teaching order: We define the three workers before the supervisor on purpose, so you see concrete roles and prompts first; the supervisor in the next section only orchestrates what you already built.

Each worker agent is specialized for a specific domain. We use create_agent from LangChain 1.x, which creates a ReAct-style agent that can use tools and reason about when to use them.

ReAct Pattern: ReAct (Reasoning + Acting) agents alternate between reasoning steps and tool-using actions. They think about what to do, use tools to gather information, and then reason about the results.

LangChain 1.x API: The create_agent function is the modern way to create agents in LangChain 1.x. It takes a model (the LLM), a list of tools, and a system_prompt to define the agent's behavior. This is cleaner and more consistent than the older agent creation methods.

Each agent gets:

  • The same LLM instance (for consistency)
  • Access to SQL tools and Python REPL (for data operations)
  • A specialized system prompt that defines its role and capabilities

InventoryManager special case: This agent works in two phases for order+inventory requests — Phase 1 checks stock (no updates), then after OrderProcessor runs, Phase 2 deducts inventory. It decides which phase it is in by inspecting conversation history for OrderProcessor's CONCLUSION.

Your Task

Create a new cell in your notebook, paste or type the following code, and execute the cell to create the three specialized worker agents.

# Create specialized agents with their tools
inventory_agent = create_agent(
    model=llm,
    tools=[python_repl, *sql_toolkit.get_tools()],
    system_prompt="""You are the Inventory Manager.
      You operate in TWO distinct phases depending on where you are in the workflow:

    PHASE 1 - CHECK (called BEFORE OrderProcessor):
    - Query inventory levels and check stock availability for the requested items.
    - Report current quantities and whether stock is sufficient for the order.
    - Do NOT update or deduct any inventory quantities in this phase.
    - End with CONCLUSION: Stock check complete. Item X has Y units available. [Sufficient/Insufficient] for the order.

    PHASE 2 - UPDATE (called AFTER OrderProcessor has confirmed the order):
    - Deduct/update inventory quantities to reflect the fulfilled order.
    - Confirm before and after quantities.
    - End with CONCLUSION: Inventory updated. Item X reduced from A to B units.

    How to determine your phase: Check the conversation history.
    - If you see NO message from OrderProcessor with a CONCLUSION → you are in PHASE 1 (CHECK only, do NOT update).
    - If you see a message from OrderProcessor with a CONCLUSION confirming the order was processed → you are in PHASE 2 (UPDATE inventory).

    Additional Instructions:
    - NEVER ask for confirmation or approval. Proceed autonomously with the task.
    - Do NOT say "Please confirm" or "Shall I proceed" — just do the work.
    - If generating code, make sure the code is correct and returns the expected value.
    - Think properly before generating code and generate all required code at once.
    - Use proper SQL syntax and verify data before any updates.
    - Keep responses focused and concise."""
)

order_agent = create_agent(

    2. Update order status and related order fields
    3. Look up order details (orders / order_items only)

    - NEVER ask for confirmation or approval. Proceed autonomously with the task.

    - Do NOT check, verify, or query inventory for stock levels or availability. Do NOT read or write the

      conversation context and proceed only with order-side changes you are allowed to make.
    - Do NOT adjust inventory quantities; InventoryManager owns all inventory mutations.
    - For order updates, confirm the new status
    - Provide specific quantities and order details for order lines only
    - Keep responses focused and concise
    Example format:
    *Analysis/Actions taken*
    CONCLUSION: Order XYZ updated. Status changed from A to B; order line details as described."""

    model=llm,

    1. Analyze sales trends
    2. Generate inventory reports
    3. Calculate key metrics
    4. Provide recommendations
    - NEVER ask for confirmation or approval. Proceed autonomously with the task.

Why separate agents? By giving each agent a focused role and specific instructions, we ensure:

  • Each agent becomes an expert in its domain
  • Clear separation of concerns (inventory vs. orders vs. analytics)
  • Better control over what each agent can and cannot do
  • More reliable and predictable behavior

5. Creating the Supervisor Agent

With InventoryManager, OrderProcessor, and AnalyticsManager defined above, you now add the supervisor: the component that reads the conversation and chooses which worker (or FINISH) should act next. The supervisor’s system prompt names the same roles students just created, so the flow of ideas is: specialists first, then orchestration.

The supervisor is the "brain" of our multi-agent system. It uses an LLM to analyze the current state and conversation history, then decides which worker agent should handle the next step. This is a powerful pattern because:

  • The supervisor can reason about complex tasks that require multiple agents.
  • It can dynamically route to different agents based on the conversation context.
  • It knows when the task is complete and should return "FINISH".

We use with_structured_output() to ensure the supervisor always returns a structured response (a Pydantic model) that we can use for routing decisions.

Your Task

Create a new cell in your notebook, paste or type the following code, and execute the cell to create the supervisor agent.

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from pydantic import BaseModel

# Create a static system prompt instead of dynamically generating it
system_prompt = """
You are a warehouse operations supervisor managing these workers: InventoryManager, OrderProcessor, AnalyticsManager.
You MUST follow domain boundaries and routing order strictly.

Worker responsibilities:
- InventoryManager: ALL inventory operations — checking stock, availability, and updating/deducting quantities.
  Works in two phases: Phase 1 (check only) before order processing, Phase 2 (update) after order is confirmed.
- OrderProcessor: Creates/updates order records, order items, order status. Does NOT touch inventory tables.
- AnalyticsManager: Reports, trends, metrics, and analysis only.

MANDATORY 4-STEP SEQUENCE for any request to "process order" or "process order AND update inventory":
  Step 1 → InventoryManager  (CHECK stock availability only — no inventory updates yet)
  Step 2 → OrderProcessor    (process/update the order using Step 1 results from conversation context)
  Step 3 → InventoryManager  (UPDATE/deduct inventory based on the confirmed order from Step 2)
  Step 4 → FINISH

LOOP PREVENTION — follow these rules exactly:
- If InventoryManager has posted a CONCLUSION about stock CHECK and OrderProcessor has NOT yet run → route to OrderProcessor.
- If OrderProcessor has posted a CONCLUSION confirming the order → route to InventoryManager for the inventory UPDATE.
- If InventoryManager has posted a CONCLUSION about an inventory UPDATE (after OrderProcessor already ran) → respond with FINISH.
- NEVER route to the same worker twice in a row unless it is the planned second call to InventoryManager (Step 3 above).
- If you are unsure whether a worker has completed its task, look for the word CONCLUSION in its latest message.

For inventory-only requests (no order processing): InventoryManager → FINISH
For order-status/lookup-only requests:             OrderProcessor → FINISH
For analytics/reporting requests:                  AnalyticsManager → FINISH
"""

options = ["FINISH", "InventoryManager", "OrderProcessor", "AnalyticsManager"]

# Set up the supervisor prompt with the static system prompt
prompt = ChatPromptTemplate.from_messages([
    ("system", system_prompt),
    MessagesPlaceholder(variable_name="messages"),
    ("system", """Review the conversation above carefully.
Identify which steps are already COMPLETED by looking for CONCLUSION statements in each worker's messages.
Based on the mandatory sequence rules, decide who should act next.
Do NOT repeat a worker that has already completed its current-phase task.
Who should act next? Or should we FINISH? Select one of: """ + str(options)),
])

class routeResponse(BaseModel):
    next: str

# Create the supervisor agent — return {"next": ...} so LangGraph can route
def supervisor_agent(state):
    supervisor_chain = prompt | llm.with_structured_output(routeResponse)
    return {"next": supervisor_chain.invoke(state).next}

Key design decisions:

  • MessagesPlaceholder allows the prompt to include the full conversation history, giving the supervisor context.
  • with_structured_output(routeResponse) ensures the LLM returns a Pydantic model with a next field, making routing reliable.
  • The supervisor returns {"next": ...} (not the raw Pydantic object) so LangGraph can merge it into state and conditional edges can read state["next"].
  • Loop-prevention rules and CONCLUSION markers keep InventoryManager from being called twice in a row for the same phase.

6. Building the LangGraph Workflow

Now we'll assemble our multi-agent system using LangGraph. LangGraph provides a powerful way to define stateful, multi-step workflows with conditional routing.

Key LangGraph Concepts:

  • StateGraph: Defines a graph where nodes share a common state.
  • Nodes: Functions that process the state and return updates.
  • Edges: Define the flow between nodes (can be fixed or conditional).
  • State: A TypedDict that holds all data shared between nodes (messages, routing decisions, etc.).

Our workflow will:

  1. Start with the supervisor
  2. Route to the appropriate worker agent based on supervisor's decision
  3. Worker agent processes the task and returns to supervisor
  4. For order+inventory requests, follow the 4-step sequence: Inventory check → Order process → Inventory update → FINISH
  5. Supervisor decides next step (another agent or FINISH) using CONCLUSION markers to avoid loops
  6. Repeat until supervisor returns FINISH

6.1 Creating the Agent Node Factory Function

Before building the graph, we need a helper function that creates node functions for each agent. This function uses Python's closure pattern to "bind" an agent and name to a node function.

Your Task

Create a new cell in your notebook, paste or type the following code, and execute the cell.

from langchain_core.messages import HumanMessage

def agent_node(agent, name):
    """Create a node function for a specific agent using closure pattern."""
    def node(state):
        print(f"Invoking {name} agent with state: {state}")
        result = agent.invoke(state)
        return {
            "messages": [HumanMessage(content=result["messages"][-1].content)]
        }
    return node
Understanding the Closure Pattern: The agent_node function demonstrates Python's closure pattern. When you call agent_node(inventory_agent, "InventoryManager"), Python creates a new inner function that "captures" or "closes over" the inventory_agent and "InventoryManager" values. This inner function is then returned and can be used later, and it will always remember those captured values even though the outer function has finished executing. This is why each node function knows which agent to invoke and what name to use when formatting messages.

6.2 Defining the Agent State

The state is a TypedDict that defines what data flows through the graph. The messages field uses Annotated[list, operator.add] which means messages are appended (not replaced) when nodes return updates, preserving the full conversation history.

Your Task

Create a new cell in your notebook, paste or type the following code, and execute the cell.

from typing_extensions import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    # The annotation tells the graph that new messages will always
    # be added to the current state
    messages: Annotated[list, operator.add]
    # The 'next' field indicates where to route to next
    next: str

6.4 Setting Up the Workflow Graph

Now we'll create the StateGraph and add all our nodes. The graph needs to know about all nodes before we can connect them with edges.

Your Task

Create a new cell in your notebook, paste or type the following code, and execute the cell.

from langgraph.graph import END, StateGraph, START

# Set up workflow
workflow = StateGraph(AgentState)
workflow.add_node("InventoryManager", inventory_node)
workflow.add_node("OrderProcessor", order_node)
workflow.add_node("AnalyticsManager", analytics_node)
workflow.add_node("supervisor", supervisor_agent)

# Conditional routing from supervisor
workflow.add_conditional_edges(
    "supervisor",
    lambda state: state["next"],
    {
        "InventoryManager": "InventoryManager",
        "OrderProcessor": "OrderProcessor",
        "AnalyticsManager": "AnalyticsManager",
        "FINISH": END
    }
)

# Entry point and return edges
workflow.set_entry_point("supervisor")
workflow.add_edge("InventoryManager", "supervisor")
workflow.add_edge("OrderProcessor", "supervisor")
workflow.add_edge("AnalyticsManager", "supervisor")

7. Running Queries Through the Multi-Agent System

Now let's test our multi-agent system! When you invoke the graph with a query, here's what happens:

  1. The query is added to the state as a HumanMessage
  2. The supervisor analyzes the query and decides which agent should handle it
  3. The selected agent uses its tools (SQL, Python) to complete the task
  4. The agent's response is added to the conversation
  5. The supervisor reviews the result and decides: continue with another agent or FINISH
  6. This continues until the supervisor determines the task is complete

This pattern is powerful because complex tasks can require multiple agents working together. For example, processing an order with inventory updates follows: InventoryManager (check) → OrderProcessor → InventoryManager (update) → FINISH.

8. Understanding the Multi-Agent Flow

Let's break down what happens when you run a query like "Process order ORD001 and update inventory accordingly":

  1. Initial State: The query arrives as a user message in the state.
  2. Supervisor Decision (Step 1): The supervisor follows the mandatory 4-step sequence and routes first to InventoryManager for a stock CHECK only.
  3. InventoryManager PHASE 1: Checks availability for the order items, reports quantities, and ends with a CONCLUSION about stock sufficiency — without updating inventory.
  4. Supervisor Decision (Step 2): Sees InventoryManager's CHECK CONCLUSION and routes to OrderProcessor.
  5. OrderProcessor: Updates order status / order records using the stock context from the conversation. Does not touch inventory. Ends with a CONCLUSION.
  6. Supervisor Decision (Step 3): Sees OrderProcessor's CONCLUSION and routes back to InventoryManager for the inventory UPDATE.
  7. InventoryManager PHASE 2: Deducts inventory quantities based on the confirmed order and ends with an UPDATE CONCLUSION.
  8. Supervisor Decision (Step 4): Sees the inventory UPDATE CONCLUSION and returns FINISH.
  9. Completion: The graph terminates and returns the final state.

This 4-step pattern (check → process order → update inventory → finish) prevents the common failure modes of updating inventory before the order is confirmed, or looping forever between the same workers.

9. Advanced Concepts and Patterns

9.1 State Management

The AgentState TypedDict is the shared memory of our system. The Annotated[list, operator.add] annotation ensures that messages are appended, not replaced. This preserves the full conversation history, allowing agents to see what previous agents have done.

9.2 Conditional Routing

The add_conditional_edges method enables dynamic routing based on state. The lambda function lambda x: x["next"] extracts the routing decision from the state, and the mapping dictionary determines which node to go to. This is how the supervisor controls the flow.

9.3 Agent Specialization

By giving each agent a focused system prompt and specific tools, we create domain experts. This is more reliable than a single general-purpose agent because:

  • Each agent has clear boundaries and responsibilities
  • Prompts can be optimized for specific tasks
  • Tools can be restricted to what's needed for each domain
  • Errors are easier to debug and contain

9.4 LLM as Supervisor

Using an LLM as the supervisor is powerful because:

  • It can understand natural language queries and map them to agent capabilities
  • It can reason about complex tasks that require multiple agents
  • It can adapt to new situations without hardcoded rules
  • It can determine when a task is truly complete

However, this also means the supervisor's decisions depend on the quality of its prompt and the LLM's reasoning capabilities. Well-designed prompts are crucial for reliable routing.
