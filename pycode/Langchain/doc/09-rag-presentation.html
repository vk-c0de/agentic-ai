Where We Are Going: RAG
Retrieval Augmented Generation — retrieve first, then generate from that context
Today we learn the ideas behind each box — especially how “retrieve similar text” is even possible.
Notes

LLMs do not contain the company handbook. RAG grounds answers in your files. The hard part is finding the right paragraphs. That starts with representing meaning as numbers.

The Problem: Comparing Strings
A computer does not “understand” English. Equality of characters is not equality of meaning.
Exact match fails

“vacation policy” ≠ “time off guidelines”

Different characters. Same idea for an HR assistant.

We need a meaning score

If two phrases mean similar things, the score should be high — even when no word is shared.

Core trick: convert each string into an array of numbers (typically between −1 and 1). Then compare the arrays with geometry instead of comparing letters.
Notes

Ask: “How would you write a function similar(a, b) for English?” Keyword overlap is brittle. Geometry on numbers is the path used in RAG.

Strings → Arrays of Numbers
Start with the smallest graphable case: an array of size 2
StringArray (2 numbers in [−1, 1])How to read it
“vacation policy” [0.80, 0.20] x = 0.80, y = 0.20
“annual leave” [0.75, 0.28] Nearby coordinates — similar meaning
“dress code” [0.10, 0.85] Different place on the graph — different topic
Each pair is a point on the 2D plane. Two numbers = two axes. That is enough to draw.
Notes

These toy numbers are for teaching. Real models output hundreds or thousands of numbers. The graph is only possible in 2D (or 3D).

Plot the Points — Then Draw Lines from the Origin
Origin (0, 0) is the starting point of every arrow
Notes

Trace each arrow with a finger from (0,0). Stress: we did not plot the words. We plotted the number pairs. Meaning became geometry.

Those Lines Are Vectors
A vector has two properties: magnitude (length) and direction (angle)

Magnitude

How long is the arrow from the origin to the point?

‖v‖ = √(x² + y²)

“vacation policy”: √(0.80² + 0.20²) ≈ 0.82

Direction

Which way does the arrow point?

Blue and green point almost the same way. Orange is closer to the y-axis.

For meaning, direction matters more than length. Two phrases about time off point the same way. A phrase about clothing points elsewhere. Similarity of meaning ≈ similarity of direction.
Notes

If students know physics: same as displacement arrows. If not: “arrow from origin.” Cosine later ignores length (it normalizes), which is why direction is the similarity story.

Generalize: Larger Arrays
Real text is too rich for 2 numbers. The same idea works in hundreds or thousands of dimensions.
A string can be converted into an array of size 2, 8, 384, or 1536. You cannot draw a 1536-dimensional arrow — but the computer can still measure how aligned two arrows are.
Notes

OpenAI text-embedding-3-small in the lab is 1536 dimensions. “High-dimensional space” just means a long list of numbers, one per axis.

Who Turns Strings into Arrays?
We do not pick the numbers by hand. A trained model does.
An embedding model is a neural network trained on huge amounts of text
Its job: take a string in, emit a fixed-length array of numbers out.
Training teaches it to notice patterns
Words and phrases that appear in similar contexts tend to mean similar things (“vacation”, “annual leave”, “PTO”). The model is rewarded when those phrases land as nearby vectors.
You call the model; you do not invent the coordinates
embed_query("vacation policy") → [0.023, -0.41, 0.67, …]
Notes

Contrast with one-hot or bag-of-words: those arrays are sparse and do not place synonyms near each other. Embedding models are trained so synonyms cluster.

Patterns → Features → Indexes
Each slot in the array is a learned feature channel — not a random float

Toy 4-D story (real models are not labeled this cleanly, but this is the right mental model):

Index Feature the model learned to encode “vacation policy” “dress code”
0Time-off / leave relatedness0.820.11
1Appearance / clothing0.050.91
2Policy / rules language0.700.68
3Money / compensation0.150.08
In a 1536-D model you usually cannot name index 417. Meaning is distributed across many indexes. Still: each number is a learned coordinate, not noise.
Notes

Be honest: we do not inspect index 47 in production. The teaching point is “structured meaning,” not “dimension 3 = salary.” Both phrases score high on “policy language” — that is why they are not opposites.

Embedded Meaning
The array is called an embedding. The model is an embedding model.
Embedding (noun)

The array of numbers that embeds (packs) the meaning of the text into a vector.

“vacation policy” → embedding vector

Embedding model

The trained network that maps any string to that array. Same model ⇒ same geometry for all your documents and queries.

If you change embedding models, you change the coordinate system. Never mix vectors from model A with vectors from model B in the same search.
Notes

Lab uses one model: text-embedding-3-small. If they re-index later with a different model, they must rebuild the vector store.

Generating Embeddings — Example Code
LangChain + OpenAI embedding model (same pattern as the lab)
from langchain_openai import OpenAIEmbeddings embeddings = OpenAIEmbeddings(model="text-embedding-3-small") sample_texts = [ "Employee vacation policy and time off", "Annual leave and holiday guidelines", "Company dress code requirements", ] sample_embeddings = [embeddings.embed_query(text) for text in sample_texts] print(len(sample_embeddings[0])) # 1536 dimensions print(sample_embeddings[0][:8]) # first 8 numbers of vector 1
Notes

embed_query is for a single string (the user question). For many chunks you typically use embed_documents. Same vector space either way.

What Comes Back
A long list of floats. Similar sentences look similar as lists — not as English.
Text: "vacation policy" → [ 0.23, -0.45, 0.67, 0.12, ...] Text: "time off guidelines" → [ 0.25, -0.43, 0.65, 0.10, ...] # close numbers Text: "employee benefits" → [ 0.12, -0.89, 0.34, -0.40, ...] # different topic

Same model

Every string is projected into the same space so comparison is valid.

Fixed length

Short or long sentence → same number of dimensions (the model pools meaning).

Ready to score

We still need a formula that turns two arrays into one similarity number.

Notes

Point at the first two rows: coordinates move together. That is “nearby arrows” in 1536-D. Next: cosine makes that a single score.

Cosine Similarity — Score from the Angle
Cosine of the angle between two arrows: 1 = same direction, 0 = right angle, −1 = opposite
cos(θ) = (A · B) / ( ‖A‖ × ‖B‖ )
Angle θcos(θ)Meaning
≈ 0°≈ 1Same direction — very similar
90°0Unrelated axes
180°−1Opposite direction

Dividing by the lengths (‖A‖ and ‖B‖) means we compare direction only, not how long the arrows are.

Notes

Dot product A·B = |A||B|cos(θ). Rearrange to isolate cosine. In RAG, “more similar” = larger cosine (or smaller cosine distance, depending on the store).

Worked Example (2D)
Same three phrases as the graph — now scored
PairDot product A·BLengthscos(θ)
vacation [0.80, 0.20]
annual leave [0.75, 0.28]		 0.80×0.75 + 0.20×0.28 = 0.656 0.825 × 0.801 ≈ 0.99
vacation [0.80, 0.20]
dress code [0.10, 0.85]		 0.80×0.10 + 0.20×0.85 = 0.250 0.825 × 0.856 ≈ 0.35
0.99 vs 0.35 — the computer now has a number that matches human intuition: time-off phrases are alike; dress code is a different topic.
Notes

Walk the arithmetic slowly. Then say: in 1536-D you do the same — sum of products, divide by lengths. Numpy does it in one line.

Cosine in Code
This is the scoring function behind “find similar chunks”
import numpy as np def cosine_similarity(vec1, vec2): return np.dot(vec1, vec2) / ( np.linalg.norm(vec1) * np.linalg.norm(vec2) ) sim_time_off = cosine_similarity( sample_embeddings[0], sample_embeddings[1] ) # high — both about leave sim_other = cosine_similarity( sample_embeddings[0], sample_embeddings[2] ) # lower — dress code # Higher similarity = more related content
Notes

Lab prints these two scores. Students should predict high vs low before they run the cell. Chroma uses the same idea internally (sometimes as distance = 1 − cosine).

Embeddings compare meaning. RAG needs your documents split into searchable pieces.

Documents from a PDF
A loader turns each page into a LangChain Document: text + metadata
from langchain_community.document_loaders import PyPDFLoader loader = PyPDFLoader("employee-handbook.pdf") docs = loader.load() # Document( # page_content="The actual text content", # metadata={"source": "employee-handbook.pdf", "page": 1} # )

page_content

The raw text the embedding model will later see.

metadata

Source file, page number — used for citations after retrieval.

Other loaders: WebBaseLoader, TextLoader, CSVLoader. Same Document shape, different source.

Notes

One PDF page is often still too large and mixed-topic. That is why we split. Metadata survives splitting so answers can say “page 12.”

Why Chunk? The Chunking Paradox
Too small loses context. Too large mixes topics and dilutes similarity search.
Goal: large enough to be meaningful, small enough to match one query.
If a 4-page chunk mixes vacation, payroll, and parking, a query about vacation gets a weak, noisy vector. If a chunk is half a sentence, the vector has no surrounding policy.
Notes

There is no universal chunk_size. Handbook lab uses 1000 characters / 200 overlap as a practical default.

Strategy 1 — Size-Based Chunking (No Overlap)
Split every N characters. Fast and predictable. Can cut in the middle of a word.
Zero overlap: each character lives in exactly one chunk. Words like “policy” can split into “polic” / “y”.

Simple loop: take characters [0:N], then [N:2N], then [2N:3N]. No step backward.

Notes

Show why retrieval fails if the query is “vacation policy” and those two words were split across chunks.

Size-Based Chunking — With Overlap
Step back by overlap characters so boundary phrases appear in two chunks
def fixed_size_chunk(text, chunk_size=500, overlap=50): chunks, start = [], 0 while start < len(text): chunks.append(text[start:start + chunk_size]) start = start + chunk_size - overlap # step back return chunks
Notes

Overlap duplicates tokens and costs more storage. Typical lab values: size 1000, overlap 200 (20%).

Strategy 2 — Recursive Character Splitting
Still size-based, but try natural boundaries first. This is what the lab implements.
Separator hierarchy: \n\n (paragraphs) → \n (lines) → . (sentences) → (words) → raw characters. Only fall back to a harsher split when a piece still exceeds chunk_size.
LangChain: RecursiveCharacterTextSplitter
chunk_size=1000 · chunk_overlap=200 · add_start_index=True (remember offset in the original page)
from langchain_text_splitters import RecursiveCharacterTextSplitter splitter = RecursiveCharacterTextSplitter( chunk_size=1000, chunk_overlap=200, add_start_index=True ) all_splits = splitter.split_documents(docs)
Notes

Recommended default for general PDFs. Students should know it is not “semantic chunking” — it is smart size-based splitting.

Strategy 3 — Document Structure-Aware
Split on headings and sections the document already defined
Each chunk stays inside one logical section. Heading metadata helps filtering and citations.

Example API: MarkdownHeaderTextSplitter with ("#", "Header 1"), ("##", "Header 2"). Best for Markdown, HTML, well-structured PDFs.

Notes

If the handbook has clear H1/H2, this often beats blind character cuts. Scanned PDFs with no structure cannot use this well.

Strategy 4 — Semantic Chunking
Split where meaning shifts, not where a character count is reached
How it works
Embed each sentence. When cosine similarity between neighboring groups drops below a threshold, start a new chunk. Lengths vary; each chunk tends to be one idea.

LangChain: SemanticChunker + an embedding model. Slower (many embedding calls). Strong on narrative / mixed-topic prose.

Notes

Ironic but useful: you need embeddings to chunk, then you embed the chunks again for the vector store. Lab does not require running this.

Chunking Strategies — Comparison
Choose by document type, not by fashion
StrategySpeedRespects structureBest for
Size-based (fixed)FastNoBaselines, uniform text
Recursive characterFastPartiallyGeneral-purpose docs (our lab)
Document structureMediumYesMarkdown, HTML, structured PDFs
SemanticSlowerBy meaningNarrative / mixed-topic prose
Lab default: recursive splitter, chunk_size=1000, chunk_overlap=200. Good enough to learn retrieval; production systems often mix structure + size limits.
Notes

If asked “which is best?”: it depends. Start recursive; add structure when headings exist; try semantic when topics wander inside paragraphs.

Retrieval: Find the Right Chunks
Embed the question. Compare to stored chunk vectors. Return the best matches.

Similarity (top-k)

Always take the k nearest neighbors. Simple default.

With scores

Same ranking, plus a number so you can see confidence.

Score threshold

Drop chunks that are not similar enough — even if k is not filled.

Notes

k=3 is common in the lab. Too small misses supporting paragraphs; too large floods the LLM with noise.

Similarity Search — Examples
Once chunks live in a vector store, search is one call
query = "What is the vacation policy?" results = vector_store.similarity_search(query, k=3) # With scores (distance or similarity, depending on backend) results_with_scores = vector_store.similarity_search_with_score( "How many sick days do employees get?", k=3 ) for doc, score in results_with_scores: print(score, doc.page_content[:200])
Try several queries
Working hours, benefits, dress code — retrieved chunks should change with the question. That is the test that embeddings + chunking are working.
Notes

Chroma often returns distance (lower = closer). Warn students not to assume “0.9 is always better” without reading the metric docs.

The Retriever Abstraction
A retriever is a consistent “documents in, query out” interface for chains and agents
retriever = vector_store.as_retriever( search_type="similarity", search_kwargs={"k": 3} ) docs = retriever.invoke("What are the company holidays?")
search_typeWhat it does
similarityStandard top-k by vector similarity
mmrBalance relevance with diversity among the returned chunks
similarity_score_thresholdKeep only results above a score cutoff

Batch: retriever.batch([q1, q2, q3]) — many questions in one call (offline eval, bulk Q&A).

Notes

Same vector store, different selection policy. MMR is the one students most often misunderstand — next slides go slow.

Why Top-k Similarity Is Not Enough
Nearest neighbors can be near each other — three copies of the same idea
Query: “What benefits do employees receive?”
Similarity search (k=3) might return three near-duplicate health-insurance paragraphs because they all sit next to the query vector.

What the user needed

A spread of the benefits landscape: health, retirement, wellness — not the same medical plan three times.

What went wrong

Relevance-only ranking has no memory of “I already picked a chunk like this.”

MMR (Maximum Marginal Relevance) picks the next chunk that is relevant to the query and dissimilar to chunks already chosen.
Notes

This is the motivation slide. Do not skip it. MMR exists because redundancy wastes the LLM context window.

MMR — The Idea and the Formula
Greedy loop: fetch many candidates, then pick k that trade off relevance vs diversity
MMR(d) = λ · Sim(d, q) − (1 − λ) · maxs ∈ S Sim(d, s)
SymbolMeaning
qThe user query
RCandidate pool (LangChain: fetch_k, e.g. 10)
SChunks already selected (starts empty)
dA candidate still in R − S
λ (lambda_mult)1 = only relevance · 0 = only diversity · 0.5 = balanced

First pick is always the most similar to the query (S is empty, so the penalty term is 0). Each later pick is penalized if it looks like something already chosen.

Notes

Read the minus sign aloud: “relevance bonus minus redundancy penalty.” λ is the mixing knob they will set in code.

MMR Worked Example — Setup
Query q = “What benefits do employees receive?” · fetch_k = 5 · we want k = 3 · λ = 0.5
IDChunk (topic)Sim(d, q)
D1Health insurance coverage0.92
D2Medical plan deductibles (almost the same as D1)0.89
D3401(k) retirement matching0.81
D4Gym and wellness stipend0.76
D5Dental/vision (still health — close to D1)0.88

Pairwise similarity we will need: Sim(D1,D2)=0.95 · Sim(D1,D5)=0.91 · Sim(D1,D3)=0.38 · Sim(D1,D4)=0.42 · Sim(D3,D4)=0.50

Pure similarity top-3 would be D1, D2, D5 — all health. Watch MMR do something different.
Notes

Write S = { } on the board. Round 1 has no penalty. Students should shout D1.

MMR Worked Example — Rounds 1 and 2
λ = 0.5 so each term is half relevance, half “how similar to the closest already-picked chunk”

Round 1 — S is empty

Penalty is 0. Highest Sim(d,q) wins. Pick D1 (0.92). Now S = {D1}.

Round 2 — MMR(d) = 0.5×Sim(d,q) − 0.5×Sim(d, D1)

d0.5 × Sim(d,q)− 0.5 × Sim(d,D1)MMR
D20.445−0.475 (0.95 with D1)−0.030
D30.405−0.190 (0.38 with D1)+0.215
D40.380−0.210 (0.42 with D1)+0.170
D50.440−0.455 (0.91 with D1)−0.015

Pick D3 (retirement). D2 and D5 were more relevant to q but too similar to D1 — they were penalized.

Notes

Pause on D2: second-highest relevance, worst MMR. That is the whole lesson in one row.

MMR Worked Example — Round 3 and Result
S = {D1, D3}. Penalty uses the max similarity to anything already selected

Round 3 — MMR(d) = 0.5×Sim(d,q) − 0.5×max(Sim(d,D1), Sim(d,D3))

dRelevance halfDiversity penaltyMMR
D20.445−0.475 (still glued to D1)−0.030
D40.380−0.250 (max vs D1/D3 = 0.50)+0.130
D50.440−0.455 (glued to D1)−0.015

Pick D4 (wellness).

Similarity top-3
D1, D2, D5 — health, health, health
MMR k=3
D1, D3, D4 — health, retirement, wellness
Notes

Same candidate pool, different selection rule. The LLM now sees three benefit types instead of one. That is why MMR helps RAG answers feel complete.

MMR in LangChain
fetch_k is the candidate pool · k is what you keep · lambda_mult is λ
mmr_retriever = vector_store.as_retriever( search_type="mmr", search_kwargs={ "k": 3, # final number of chunks "fetch_k": 10, # candidates to rerank with MMR "lambda_mult": 0.5 # 0 = max diversity, 1 = max relevance } ) docs = mmr_retriever.invoke("What benefits do employees receive?")
Compare side by side with search_type="similarity" on the same query. If similarity returns near-duplicates and MMR returns different sections, MMR is doing its job.
Notes

If fetch_k equals k, MMR has no room to choose. fetch_k should be clearly larger than k (10 vs 3 in the lab).

Storing Vectors in Chroma
A vector store persists embeddings and runs fast nearest-neighbor search
# Store phase Document → Embedding → Chroma # Query phase Question → Embedding → nearest vectors → original chunks
Why not a Python list?
Thousands or millions of chunks need an index, disk persistence, and a search API.
Chroma in the lab
Local, easy, writes to ./chroma_db so you can reuse without re-embedding every time.
from langchain_community.vectorstores import Chroma vector_store = Chroma.from_documents( documents=all_splits, embedding=embeddings, persist_directory="./chroma_db" )
Notes

from_documents embeds every chunk, then stores text + vector + metadata. Same embeddings object must be used at query time.

Retrieval Strategy on the Store
Chroma holds the vectors. The retriever chooses how to pick among them.
Indexing quality (chunking + embedding model) sets the ceiling. Retrieval strategy decides which of those chunks actually reach the prompt.
Notes

Tie-back: students now have store + policy. Last section is how generation is wired — always retrieve vs let an agent decide.

Traditional RAG — Always Retrieve, Then Generate
Fixed pipeline: every question triggers search, then one LLM call with that context

Faster

Usually one model call per question.

Predictable

No tool-choice. Search always happens.

Cheaper

Fewer tokens spent on “should I search?”

Limitation: cannot skip retrieval for “hello”, and cannot run two different searches on its own for a comparison question.

Notes

Lab implements this with LangChain middleware: @dynamic_prompt runs similarity_search, then returns a system message that already contains handbook pages.

Traditional RAG — Middleware Pattern (Lab)
Context is fetched immediately before the model runs, then stuffed into the system prompt
@dynamic_prompt def prompt_with_context(request: ModelRequest) -> str: last_query = request.state["messages"][-1].content retrieved_docs = vector_store.similarity_search(last_query, k=3) docs_content = "\n\n---\n\n".join( f"Page {doc.metadata.get('page')}:\n{doc.page_content}" for doc in retrieved_docs ) return ( "You are an HR assistant. Use this handbook context.\n" "If it is missing, say you do not have it.\n\n" f"Context:\n{docs_content}" ) rag_pipeline = create_agent(llm, tools=[], middleware=[prompt_with_context])
Notes

tools=[] is intentional: retrieval is not a tool the model chooses; middleware always injects context. Greeting still retrieves (wasted search) — that is the tradeoff.

Agentic RAG — The Model Decides When to Search
Retriever becomes a tool. The agent may call it zero, one, or many times.
Typical loop
1) Read the question · 2) Decide whether the handbook is needed · 3) Search (maybe twice: sick leave, then vacation) · 4) Combine evidence and answer.

Cost: more LLM calls and higher latency. Benefit: greetings skip search; comparison questions can retrieve twice.

Notes

Demo in lab: vacation policy (one tool call), sick vs vacation (two calls), “Hello” (zero calls). That three-way contrast is the teaching payoff.

Agentic RAG — Tool + Agent (Lab)
The tool wraps similarity_search. The system prompt says when to use it.
@tool def retrieve_employee_handbook(query: str): """Search the employee handbook for policies, benefits, time off...""" retrieved_docs = vector_store.similarity_search(query, k=3) return "\n\n".join( f"Source (Page {doc.metadata.get('page')}):\n{doc.page_content}" for doc in retrieved_docs ) agent = create_agent(llm, [retrieve_employee_handbook], system_prompt="You are an HR assistant. Use the tool for handbook questions. Greetings need no tool.")
Notes

Tool docstring matters: the model uses it to decide. A vague docstring → random tool use. Stream events so students see the thought/tool/answer sequence.

Same vector store. Different control over retrieval.

One-Sentence Takeaway
Convert text to vectors with an embedding model, compare them with cosine, store chunks in a vector database, retrieve with a strategy (similarity or MMR), then either always stuff context into one prompt or let an agent decide when — and how often — to search.
